# VelaShell Docker 面板插件

在 VelaShell **已经连上的 SSH 会话**上,开一个完整的 Docker 管理面板:容器、镜像、卷、
网络、Compose 项目,外加日志、统计、进程表与空间回收。

命令面板(`Ctrl+P` / `Ctrl+K`)里搜 **Docker** → *打开 Docker 管理面板*。

---

## 一、它为什么长这样

### 1. 走 `docker` CLI,不走 daemon 的 HTTP API

管理远端 Docker 有两条路,这个插件选了后一条:

| | 需要服务端做什么 | 代价 |
| --- | --- | --- |
| daemon HTTP API | 把 daemon 暴露在 TCP 端口上,或把 unix socket 转发出来 | 那是一个**root 等价、默认无认证**的端口;socket 转发还要额外的中继进程 |
| `docker` CLI over SSH | **什么都不用做** | 每个动作一次 SSH exec;拿不到流式事件 |

绝大多数生产机不会为了一个管理面板开 2375。而 `docker` 命令在每台装了 Docker 的机器上
都在,权限模型就是用户自己的 —— 面板因此**零服务端配置**即可用,也没有给主机开出新的
攻击面。代价写在下面的"已知边界"里。

### 2. 复用会话,不自己建连接

面板没有自己的连接类型,也没有连接对话框。它列出宿主当前**已连接**的 SSH 会话,
让你挑一条。凭据永远不出宿主核心(SDK v1 的硬规则:插件不能自行发起连接),
插件连一次密码都见不到。

### 3. 退出码是自己补回来的

宿主的远程执行能力只回标准输出 —— 没有标准错误,也没有退出码。而 `docker` 把绝大多数
错误写在标准错误上。所以每条命令都被包成:

```sh
sh -c 'export LC_ALL=C LANG=C; { <命令>
} 2>&1; printf "\n__VELA_DOCKER_RC:%d__\n" "$?"'
```

- 套一层 `sh -c`:用户的登录 shell 可能是 fish/csh,那里没有 `$?`;
- `2>&1`:不合并就会出现"删除失败了但界面一片安静";
- 末尾哨兵:把退出码带回来,取输出里**最后**一次出现的那个(容器日志恰好印出同样的串
  也不会误判)。

所有拼进命令的用户输入都过 `Sh.Quote`(POSIX 单引号,内部单引号转 `'\''`)。
唯一例外是各表单里的**额外参数**一栏 —— 那一栏的用途就是"我要自己写参数",
引用了反而什么都传不进去;界面上写明了它与在终端里手敲同权。

### 4. 一次刷新 = 一次往返

容器页每次刷新要列表、四个计数、还有 CPU/内存三样东西。分三次调用在本机看不出差别,
在一条 200 ms 往返的跨洋链路上就是每 5 秒卡半秒。它们被拼成**一条**脚本,按哨兵切回三段。

## 二、面板里有什么

### 容器

列表按"在跑的排前面"排,左侧一道色条标状态(绿=运行 / 黄=暂停 / 红=不健康 / 灰=停止),
compose 起的容器在名字下面带项目名。

启动 · 停止 · 重启 · 暂停 · 恢复 · 强杀 · 删除 · 重命名 · 改重启策略 · 复制 id,
**全部支持多选批量**;批量的结果逐个目标分别判定,状态栏报"成功 8、失败 2 —— 原因",
而不是把整批说成"失败"。

**进容器**:把 `docker exec -it <id> bash 2>/dev/null || docker exec -it <id> sh` 敲进
这条会话的终端标签(宿主会为此弹一次授权)。面板不自己开伪终端 —— 那样只会做出一个更差的
终端,而走宿主的终端标签意味着补全、快捷键、会话日志、录制、ZMODEM 全都在。

抽屉里:**详情**(inspect 的完整 JSON)· **日志** · **进程**(`docker top`)·
**文件变更**(`docker diff`)· **端口**。

### 日志

行数(100 / 500 / 2000 / 10000)、时间戳、本地包含过滤、自动换行、复制全部。

**"跟随"不是 `docker logs -f`** —— 远程执行是一次性的,`-f` 永远不返回,只会挂到超时
然后把整段丢掉。这里是按自动刷新的间隔用 `--since <上一条的时间戳>` 增量续取,并把
`--since` 闭区间重复回来的那一行去掉。所以跟随**依赖时间戳**,打开它会把时间戳一起打开。

### 镜像

拉取(可指定平台 / 全部标签)· 推送 · 打标签 · 删除 · 清理悬空镜像 · 复制 id ·
**运行…**(一个完整的 `docker run` 表单:名字、端口、卷、环境变量、网络、重启策略、
`-d`、`--rm`、覆盖命令、额外参数)。抽屉里有 inspect 与构建历史。

拉取与运行的完整输出摆进"执行记录"抽屉 —— 层复用、摘要、警告都在那儿,进度条的回车
重画已经折叠成每层一行。

### 卷 / 网络

卷:新建(驱动 + 驱动选项 + 标签)· 删除 · 清理未使用。
网络:新建(驱动 / 子网 / 网关 / internal / IPv6)· 接入容器 · 摘除容器 · 删除 · 清理未使用。
内置的 `bridge` / `host` / `none` 删不掉,所以按钮直接不给点,而不是让你撞一条 docker 的错误。

### Compose

`docker compose ls --all` 列出项目;每个项目可以 up -d · start · stop · restart ·
pull · build · down。抽屉里有服务列表(`ps -a`)、合并日志、展开后的配置(`config`,
顺带就是一次语法校验),以及**直接编辑远端 compose 文件**(经 SFTP 读写,不经 shell)。

compose 命令同时钉住 `-p`、`-f` 与 `--project-directory`:

- 光给项目名,compose 找不到 yml(它不记得项目从哪来);
- 光给文件,项目名会按目录名重新推导,`down` 掉的可能是另一个项目;
- 不给 project-directory,yml 里的 `./data` 会以**登录目录**为基准解析 —— 一个安静地挂错盘的 bug。

`compose ls` 只认得起过至少一次的项目。别的用「打开文件…」给一个远端路径,
它会作为一个项目留在列表里。

### 系统

`docker version` / `docker info` / `docker system df -v` 三块原文,加一排回收:
已停止的容器 · 悬空镜像 · **全部未使用镜像** · 构建缓存 · 以上全部 · **以上全部 + 卷**。

## 三、护栏

破坏性操作一律走**面板内**的确认框(不是飘在屏幕中央的弹窗 —— 同时开着生产与测试两台
机器时,一个不写清是哪台主机的"确定删除 3 个卷吗"是这个插件能犯的最贵的错误)。
确认框里摆的是**那条真命令**,不是一句概括。

两档:

- 一般破坏性(删容器、删镜像、删网络、compose down、多数 prune):后果说明 + 危险色按钮;
- **会丢数据**(删卷、`compose down -v`、`system prune --volumes`、覆盖远端 compose 文件):
  额外要求手打确认串,与删仓库同款 —— 因为后果同款。

"强杀"单独一档:SIGKILL 不给进程刷缓冲、关连接的机会,所以它也要过确认,并且文案里
明说"除非它已经卡死,否则该用停止"。

## 四、权限与设置

面板头部右侧的 **设置**:

- **以 sudo 执行 docker** —— 用的是 `sudo -n`(**绝不**弹口令提示)。当前账号不在 `docker`
  组时,面板会直接说"没有 docker socket 的权限,把账号加进 docker 组,或者打开这个开关",
  而不是给一个红叉。`sudo -n` 遇到要口令的规则会如实报出来,让你去配 NOPASSWD 或把它关掉。
- **DOCKER_HOST** / **DOCKER_CONTEXT** —— 留空即用远端默认。

这两项**按主机记忆**(换条会话再连上还是同一套),存在插件私有的 KV 里;
自动刷新间隔、显示选项、日志行数是全局的。插件不写任何机密。

## 五、已知边界(有意为之)

| 边界 | 为什么 |
| --- | --- |
| 只能管**已经连上**的 SSH 主机 | SDK v1:插件不能自行发起连接。这是契约,不是绕过它的理由 |
| 没有实时事件流(`docker events`) | 远程执行是一次性通道;面板用固定间隔刷新代替,最短 5 秒(§9 的纪律) |
| `docker logs -f` / `stats` 流式 | 同上。日志用 `--since` 增量续取,统计用 `--no-stream` 快照 |
| `docker exec` 的交互式会话在**终端标签**里,不在面板里 | 插件自己再造一个终端只会更差 |
| compose v1(独立的 `docker-compose`)列不出项目 | v1 根本没有 `ls` 子命令。这时项目列表为空,请用「打开文件…」按路径操作;其余动作照常 |
| `docker build` 只在 compose 项目上有(`compose build`) | 单独的 `docker build` 需要一个构建上下文目录,那属于终端里的活儿 |
| 没有 `docker login` | 口令走命令行参数会留在进程表与 shell 历史里。私有仓库请先在终端标签里 `docker login`,凭据落在远端的 `~/.docker/config.json`,之后面板的拉取/推送照常 |
| Windows 容器未验证 | 命令是通用的,但列的解析与 `docker top aux` 是按 Linux 写的 |

## 六、构建与安装

```bash
dotnet build                                  # 开发构建
dotnet test                                   # 67 个单测,不需要宿主
dotnet build -c Release -t:PackVpx            # → bin/vpx/velashell.dockerpanel-0.1.0.vpx
```

装上去:侧栏插件图标 → 插件管理页 → **安装 .vpx…**,或 `vela-plugin install <包>`。

开发内环(改完重启宿主即最新代码,插件在管理页带 **DEV** 角标):

```bash
vela-plugin dev-link bin/Debug/net11.0
```

断点:插件是 `inProcess` 的,IDE"附加到进程"选 `VelaShell` 即可。

## 七、验证清单(界面部分靠手测)

单测覆盖的是命令拼装、输出解析、退出码回传、行合并、确认闸门与表单;
**界面行为**没法在没有宿主的进程里可信地验证,所以下面这几条请在真机上过一遍:

1. 没有已连接会话时打开面板 → 头部提示"选一条已连接的 SSH 会话开始",按钮全灰;
2. 连上一台**没装 docker** 的机器 → 提示"找不到 docker",而不是一片空列表;
3. 连上一台当前账号不在 `docker` 组的机器 → 提示里明确给出两条出路;打开 sudo → 恢复正常;
4. 选中多个容器 → 停止 → 状态栏报成功/失败计数;其中一个已经停了 → 那一条单独标失败;
5. 打开日志 + 跟随 → 新日志追加在末尾,**没有重复行**;
6. 自动刷新开着时选中一行 → 刷新后选中态还在,CPU/内存在原地更新;
7. 删卷 → 必须手打 `delete` 才能按下确认;
8. 编辑 compose 文件 → 保存 → 必须手打 `save`;保存后 `config` 能解析;
9. 切明暗主题 → 面板配色立即跟随(全部走 `{DynamicResource Vela*}`);
10. 关掉面板 → 后台刷新循环停止(日志里不再有本插件的 exec 记录)。
